# YuAgent 代码审查与优化方案

日期：2026-09-07。审查基线：`main` / `199ffa9`，检查开始时工作区干净。

## 结论与范围

项目已有可继续迭代的基础，建议做针对性修复，不进行全项目重写。优先级是：工具隔离与凭据保护 → 配置和参数正确性 → 连接与取消可靠性 → 经测量确认的性能优化 → 局部结构整理。

本轮进行了源码目录扫描，并重点阅读 Java 对话、MCP、容器、RAG，Go 网关会话与部署，前端聊天/预览以及 Compose、Dockerfile 和 CI。不是逐行审计全部代码，也不是生产安全认证。以下区分可从源码确认的行为与仍需复现、压测的影响；本轮没有调用付费模型、重启服务或重新运行全套测试。历史测试结果不作为当前链路全部正常的证明。

值得保留的已有改进：聊天页用请求标识防止旧会话分片串写，用 requestAnimationFrame 合并消息内容更新；ChatSessionManager 用实例匹配避免旧回调删除新会话；MCP provider 关闭具有幂等保护；混合检索的两个分支共享截止时间；常用查询已有索引补丁。

## 具体发现

### 1. P1：托管 MCP 共享工具集合，缺少用户和 Agent 级边界

- 证据：`McpUrlProviderService.java:35` 优先把 hosted 工具送到共享网关；`MCPGatewayService.java:89` 忽略传入的服务名，统一返回 `/stream`，不携带用户工作区；`mcp-gateway/internal/sessions/manager.go:64` 连接工作区内全部运行服务。`AgentToolManager` 没有在聚合结果上再实施当前 Agent 的工具允许列表。
- 影响：默认工作区已有 A、B 两个服务时，只配置 A 的 Agent 也可能拿到 B。多用户同名服务还会复用首个正在运行的配置，涉及凭据和工具权限混用。源码路径已确认，跨用户端到端复现待补。
- 方案：先给每个用户建立服务端控制的工作区/凭据边界，部署与连接使用一致的身份；再将当前 Agent 获准工具限定到会话，并在执行入口再次校验。不能只在页面或提示词中隐藏工具。服务标识包含工具版本和配置身份，避免仅按展示名称复用。
- 验收：两个测试用户使用同名工具、不同假凭据，工具列表与调用结果完全隔离；只配置 A 的 Agent 无法执行 B，即使直接构造 B 的工具调用请求。

### 2. P1：网关日志会记录含凭据的配置

- 证据：`mcp-gateway/internal/admin/deploy_api.go:63,77` 用 `%v` 打印部署请求和配置；`MCPServerConfig` 包含原始 `Env`，没有脱敏输出实现。Java 还把网关密钥拼入 URL，网关入口启用了默认访问日志（`cmd/mcp-gateway/main.go:77`）。
- 影响：例如 `MCP_REMOTE_AUTH_ACCESS_TOKEN` 可能进入普通 INFO 日志；仅对 Java 的某一条 URL 日志脱敏不能覆盖整个链路。
- 方案：部署日志仅记录服务名、传输类型、状态和耗时；新客户端使用 Authorization 请求头，访问日志统一清洗敏感查询参数。旧 query 鉴权按兼容需求过渡，不突然切断旧客户端。
- 验收：使用唯一假 token 完成部署、初始化、调用、失败重试，检查所有测试日志均不含该值；日志仍能定位失败阶段。不要用真实密钥做泄漏测试。

### 3. P1：同端点去重丢失后续工具预设参数

- 证据：`AgentToolManager.java:94` 检测到重复 URL 就 `continue`；预设参数在后面的 `107` 行才处理，因此只有首个服务的预设进入 client 包装器。
- 影响：同时启用多个共享网关工具时，第二个及之后服务的预设不会生效。单工具成功无法覆盖这个情况。
- 方案：先按连接身份分组，合并组内每个服务的预设，再创建一个连接。预设键使用实际发布的工具命名空间，冲突明确报错。当前 `PresetParametersMcpClient` 是“整体替换参数”，这是已有兼容语义，不能在重构中悄悄改为合并。
- 验收：A、B 共用端点，两者预设都传给正确工具；交换配置顺序结果一致；未配置预设的工具参数保持原样。

### 4. P1：重新部署运行中的同名服务不会更新配置

- 证据：`mcp-gateway/internal/workspaces/workspace.go:72` 对 Running/Starting 服务直接返回 `existed`，没有比较新旧 URL、Env 或 Args。Java 对话准备阶段仍调用 `/deploy`。
- 影响：用户改了 key 或地址，再试可能继续用旧配置。此行为由代码确认，但是否解释某次历史 Unauthorized 不能仅凭此断定。
- 方案：部署语义明确为“确保指定版本配置就绪”：相同配置复用；配置变化执行受控更新/重建。失败时记录实际生效版本与错误，不能报告新配置已生效。与第 1 项的身份隔离一起设计。
- 验收：连续提交完全相同配置不会重启；从假配置 A 改为 B 后，下次新会话使用 B；更新失败时状态可见，旧会话按约定处理。

### 5. P1：SSE 首次刷新缺失，初始化和调用超时没有贯穿整个链路

- 证据：`mcp-gateway/internal/gateway/streamhttp.go:296` 写状态码后没有立即 Flush，只有后续事件或 30 秒心跳才 Flush。`SessionManager.CreateSession` 顺序初始化下游，`session.go:320` 使用独立的 Background 超时上下文；Java 又有自己的连接/初始化超时。
- 影响：无主动事件时，真实 HTTP 客户端可能迟迟收不到 SSE 响应头；多个慢服务会串行累积等待。具体用户延迟需真实 HTTP 测试确认，不能把所有历史超时都归因于协议探测。
- 方案：订阅建立后立即刷新 SSE 响应；为初始化阶段传递统一截止时间和取消信号，失败连接显式释放。协议策略集中管理，并分别验证聚合端点与单服务代理端点；单服务代理实际转发下游，不能仅因网关返回一个版本字符串就认定全部兼容。需要并发时采用有上限的并发。
- 验收：没有任何下游通知时客户端也能在本地 1 秒内收到 SSE 响应头；两台慢工具不会使总初始化时间按服务数翻倍；断开请求后握手按约定终止；协议、tools/list、tools/call、关闭均有真实 HTTP 合约测试。

### 6. P1：取消主要停止展示，资源关闭依赖后续回调

- 证据：`ChatSessionManager.java` 中取消标记状态并完成 SseEmitter，没有持有模型请求/MCP 资源的取消句柄；`AbstractMessageHandler.java:516` 在后续回调中才检查取消。完成回调中的持久化、追踪等操作位于 `closeToolProvider` 之前，未统一用 finally 保证清理。MCP 客户端构造失败也在现有 client.close 的保护范围外。
- 影响：慢上游不继续回调时，停止聊天可能不会立即释放请求；回调中数据库等操作抛错时，清理可能遗漏。外部模型是否继续计费需按实际请求验证，当前不能承诺停止即停止计费。
- 方案：让一次聊天执行对象拥有连接、工具资源和结束状态；成功、异常、超时、用户取消统一走幂等收尾。接入 SDK 支持的取消机制；对于不能中止的外部调用，设置硬超时并阻止继续发起工具调用。客户端创建失败也释放 transport。
- 验收：用可控慢模型/慢工具验证取消后不再产生新调用；注入保存消息失败仍关闭资源；重试/旧回调不会终止新请求；成功完成与失败完成不会重复登记。

### 7. P2：RAG 原问题被 HyDE 输出覆盖

- 证据：`HybridSearchDomainService.java:77` 调用 HyDE 后 `config.setQuestion(hypotheticalDocument)`；关键词检索和重排也使用修改后的 question。HyDE 的同步生成发生在两个检索分支的 30 秒预算开始之前。
- 影响：生成文本一旦偏离原问题，关键词和重排会一起偏移；关键词搜索还必须等待一次模型生成。两个分支使用默认公共线程池处理阻塞任务，负载影响待压测。
- 方案：保留 immutable 的 originalQuery；仅向量分支使用可选扩展文本，关键词和重排使用原问题。关键词分支提前启动，HyDE/向量/重排纳入明确总预算，并使用有界执行器及底层调用超时。
- 验收：假设文档故意偏题时仍按原始关键字检索和重排；无 HyDE 模型时不产生无意义异常；固定知识库题集对比召回质量、请求耗时和模型调用次数。

### 8. P2：本机可运行，但部署路径与产物可复现性仍不充分

- 证据：`deploy/docker-compose.yml:149` 默认写死 `/Users/yuyu/Desktop/...`。`ContainerAppService.java:530,755` 在 Java 所在文件系统创建目录，再把相同字符串作为宿主机 Docker bind 源路径；Compose 未把这个根目录映射进后端。创建失败时会落到容器 `/tmp`，未必是宿主可用目录。
- 影响：宿主机路径与后端容器路径可能是两个不同目录；换机器、换用户、清理目录时行为不一致。此前手动复制代码进运行容器也不等同于从提交重建镜像。
- 方案：明确区分宿主机目录与后端可访问目录，建立一致挂载，或采用命名卷方案；校验失败明确报告，不回退到错误文件系统。模板镜像与启动参数使用同一解析逻辑，兼容仓库端口、tag、digest。通过源码构建并标注提交号的镜像启动，健康信息可核对版本。
- 验收：在新的临时部署目录完成构建、启动、重启；标记文件在正确宿主目录可见并持久保留；运行提交号与待交付提交一致。保留原数据库，验证环境使用独立 Compose 项目与卷。

### 9. P2/P3：测试与前端抽象尚未覆盖最容易回归的场景

- 证据：主 CI 的 `ci.yml` 只有 Java 和前端任务，没有网关 Go 测试；前端有 lint/build，但 package.json 没有测试脚本。`AgentToolManagerTest` 当前只验证关闭幂等。聊天页约 903 行，预览页约 928 行；预览逐分片更新消息数组，而聊天页已有按帧更新，两套实现已经出现差异。
- 方案：把本轮缺陷对应的少量合约测试纳入 CI，增加“模型请求 → 实际工具调用 → 工具结果进入回答”的可控冒烟测试。先抽取共享流式消息处理 hook/reducer，再保留不同页面自己的布局。网关大文件仅在相关功能修复时按职责拆分，不以行数作为目标。
- 验收：测试断言工具实际被调用及参数，而不是仅断言回答为 15；切换会话、取消、分片错误、最终消息落盘均有覆盖。固定 200 条历史消息、长 Markdown 输出对比渲染次数和交互响应；性能是否改善以测量为准。

## 分阶段实施

每个阶段分别提交、验证、记录结果。以下为单人有效工作量的粗估，不是模型额度或完成时间承诺；依赖下载及外部网络排障另计。

| 阶段 | 范围 | 交付与验收 | 粗估 |
| --- | --- | --- | --- |
| A：修正确性 | 第 1–4 项；建立对应测试夹具 | 工具隔离、预设不丢、配置切换生效、日志无假 token；小提交可回退 | 2–3 个工作日 |
| B：修可靠性与延迟 | 第 5–8 项 | SSE 及时建立、取消和失败释放资源、RAG 保留原问题、可从源码重建启动；记录冷/热耗时 | 2–3 个工作日 |
| C：按证据整理 | 第 9 项、热点测量后的小重构 | CI 纳入网关和关键冒烟；必要时统一聊天状态逻辑 | 1–2 个工作日，可后置 |

第一批建议先做“假 token 日志测试及脱敏、共享端点双工具预设复现、SSE 首次响应测试”三个有明确边界的小改动，同时设计用户/Agent 隔离。多用户上线前必须完成第 1 项。测试可使用本地假模型和固定 MCP 服务，真实模型只做少量最终验收。

性能基线至少区分：无工具、单工具、双工具、慢工具失败、知识库查询；分开记录准备工具、初始化、首个模型 token、工具执行、持久化的耗时。重复执行固定用例后报告中位数和尾部延迟；不能用一次成功或主观体验宣布“提速多少”。

## 停止条件与暂缓事项

- 已列出的首要缺陷有失败复现与修复后回归，构建/相关测试通过，独立环境可稳定启动，即结束这一轮。
- 不升级全套依赖、不更换整体框架、不为长文件逐个拆分、不添加缺乏测量依据的缓存或连接池。
- Skill Center 属于后续产品功能。工具身份、权限、配置版本稳定后，再设计 skill 引用工具的方式。
- 完整安全审计、生产容量认证及所有页面逐行审查不在本方案已完成的范围内。
